## 2. 항목 채점 규칙

각 항목은 `levels`의 **0 / 1 / 2** 중 하나로만 판정한다.

| 점수 | 의미 |
|---|---|
| **0** | 부재 또는 정의된 하한 조건에 해당 |
| **1** | 부분 충족. 조건은 있으나 범위·품질·일관성 중 하나가 미달 |
| **2** | 충족. 정의된 상한 조건을 모두 만족 |
| **null** | **미판정.** 데이터 수집 실패 또는 수동 검증 미수행 |

### 2.1 판정 원칙

1. **levels 문구를 그대로 적용한다.** 채점자의 재량 해석을 금지한다.
   문구가 모호해 판정이 갈리면 rubric 문구를 고치지, 그 자리에서 해석하지 않는다.
2. **경계값은 하위 등급으로 내린다.** 예: `P2-05` 평균 어절 수가 정확히 18.0이면
   "18 이하"에 해당하므로 2점. "18~25"와 "18 이하"가 겹치는 경계는 **상위 등급 조건이
   먼저 평가되고 만족하면 그 등급**을 준다.
3. **근거 없는 점수를 금지한다.** 모든 항목은 `item_result.evidence[]`에 최소 1건의
   근거(url / snippet / metric / screenshot)를 남긴다. 근거가 없으면 `score = null`이다.
4. **1점을 기본값으로 쓰지 않는다.** 확인하지 못한 항목은 1점이 아니라 null이다.
   미확인을 부분 충족으로 처리하면 ARS가 체계적으로 상향 편향된다.

## 3. ARS 산식

### 3.1 Pillar 정규화

```
raw_p      = Σ score(i)          for i ∈ items(p) where score(i) ≠ null
max_raw_p  = 2 × |{ i ∈ items(p) : score(i) ≠ null }|
normalized_p = raw_p / max_raw_p          ∈ [0, 1]
weighted_p   = normalized_p × weight_p
```

**분모는 전체 항목 수가 아니라 "채점된 항목 수"다.** 미판정 항목을 0점으로 처리하면
"확인 못 했다"가 "없다"로 둔갑한다. 대신 미판정 항목 id를 `plane_b.coverage.unscored_item_ids`에
전부 나열해 공시한다.

한 Pillar의 채점 항목이 **judgeable 항목의 50% 미만**이면 그 Pillar의 점수를 보고하지 않고
`normalized_p = null`, ARS 계산에서 해당 weight를 제외한 뒤 나머지를 100으로 재정규화한다.
그리고 리포트 최상단에 커버리지 부족 경고를 노출한다.

**"전체"가 아니라 "judgeable"인 이유(rubric v1.4.0~)**: `unavailable_kind`가
`not_applicable`(판정 대상이 이 사이트에 존재하지 않음) 또는 `design_limit`(단일 관측으로는
원리상 판정 불가)인 항목은 이 Pillar의 항목 수 자체에서 뺀다. 예를 들어 P5(7항목)에서
`P5-04`가 `not_applicable`이면 judgeable은 6이고, 50% 기준은 3.5가 아니라 3이다.
반대로 `inconclusive`(대상은 있으나 확인 실패)는 judgeable에서 빼지 않는다 — "그 사이트에
외부 링크가 없다"와 "외부 링크 확인이 60%나 막혔다"는 같은 미판정이라도 성격이 다르고,
후자를 분모에서 빼면 측정 실패가 조용히 커버리지를 부풀린다. 6분류 전체 정의와 분모 산식은
§8을 참조한다.

`judgeable == 0`인 Pillar(그 Pillar의 모든 항목이 `not_applicable`/`design_limit`)는
같은 제외·재정규화 절차를 적용하되, 리포트 사유를 "커버리지 부족"이 아니라
**"이 Pillar는 이 사이트에 적용되지 않음"**으로 구분해 표기한다(§8.4). 원인이 측정
실패가 아니라 구조적 불일치이므로 같은 문구로 뭉치면 오해를 부른다.

### 3.2 ARS

```
raw_ARS = Σ_p weighted_p                       (5 pillar 합, 값역 0~100)

ARS = min(raw_ARS, gating.max_score_when_blocked)   if gating.triggered
    = raw_ARS                                        otherwise
```

`raw_ARS`와 게이팅 적용 후 `ARS`를 **둘 다** 리포트에 남긴다 (스키마 강제).
게이팅으로 깎인 점수를 감추면 "무엇을 고치면 몇 점이 풀리는지"가 보이지 않는다.

### 3.3 계산 예

- P1: 채점 10/10, raw 14 → 14/20 = 0.700 → ×25 = 17.50
- P2: 채점 10/10, raw 16 → 16/20 = 0.800 → ×25 = 20.00
- P3: 채점 8/9(P3-08 미판정), raw 11 → 11/16 = 0.688 → ×20 = 13.75
- P4: 채점 9/9, raw 6 → 6/18 = 0.333 → ×20 = 6.67
- P5: 채점 6/6, raw 8 → 8/12 = 0.667 → ×10 = 6.67

`raw_ARS = 64.59` → 게이팅 미발동 → **ARS = 64.6**
(P4 정규화 0.333 → 이 브랜드는 `avr-model.md` §4.1의 Q2 처방 후보다.)

## 4. 게이팅 규칙

```yaml
gating:
  max_score_when_blocked: 40
```

### 4.1 발동 조건

`blocking: true`인 항목이 **0점**을 받으면 발동한다. 현재 blocking 항목은 2개뿐이다.

| 항목 | 제목 | 0점 조건 요약 |
|---|---|---|
| `P1-01` | AI 크롤러 접근 허용 | 전면 Disallow(AI 봇 개별 허용도 없음), AI 봇 6종 전부 차단, 또는 재시도 후에도 5xx |
| `P1-03` | JavaScript 없이 본문 렌더링 | JS 비활성 HTML 본문이 JS 실행 후 대비 30% 미만 |

### 4.2 왜 이 둘만인가

이 두 항목은 다른 43개 항목과 **성질이 다르다.** 나머지는 "점수가 깎이는" 문제지만
이 둘은 **도달 자체가 성립하지 않는** 문제다. 완벽한 스키마도, 완벽한 문서 구조도,
크롤러가 페이지를 받아가지 못하면 정확히 0의 가치를 갖는다.
가산 방식 점수 체계는 이 비선형성을 표현하지 못하므로 상한(cap)으로 강제한다.

blocking을 3개 이상으로 늘리면 게이팅이 흔해져 "40점 만점 리포트"가 양산되고
변별력이 사라진다. **2개로 고정한다.**

### 4.3 상한값 40의 근거

- 게이팅 발동 브랜드는 사실상 AI 답변 파이프라인 밖에 있다. 그럼에도 0점으로 두지 않는 이유는
  나머지 항목의 상태가 **해제 이후 남는 작업량**을 알려주기 때문이다.
- `scoring.md`의 ARS 임계값 60보다 확실히 낮아야 한다. 게이팅 상태에서 "ARS 높음"
  사분면으로 분류되는 일이 발생해서는 안 된다. 40은 60에 대해 20점 마진을 둔 값이다.
- 45항목(v1.3.0 기준)이 전부 1점(부분 충족)이면 `raw_ARS = 50`이다. 항목 수와 무관하게
  Pillar 정규화가 이를 상쇄하므로 이 값은 v1.0.0(44항목) 이후 모든 버전에서 불변이다. 상한 40은 그보다도 낮으므로
  **게이팅 브랜드는 항상 "전면 미충족"보다 낮게 나온다.** 의도한 결과다.

### 4.6 robots.txt 상태 코드 — 4xx 와 5xx 는 정반대다 (rubric v1.2.0~)

v1.1.0 은 404 와 5xx 를 한 묶음으로 P1-01 0점 처리했다. **오진이었다.**
RFC 9309 는 둘을 정반대로 규정한다.

| 상태 | RFC 9309 | 크롤러 동작 | P1-01 |
|---|---|---|---|
| 4xx (404 포함) | §2.3.1.3 Unavailable | *"the crawler MAY access any resources on the server"* — **전체 허용** | **1** |
| 5xx | §2.3.1.4 Unreachable | *"the crawler MUST assume complete disallow"* — **전체 차단 가정** | **0** |
| 그 외 비200 (401·403 등) | 규정 없음 | — | `unavailable` |

404 를 0점으로 두면 **robots.txt 를 두지 않은 정상 사이트**(AI 크롤러가 전부 들어올 수 있는
상태)가 blocking 게이팅에 걸려 총점 40 으로 잘린다. 실측으로 ARS 96.2 → 40.0, **56점 오차**다.
robots.txt 부재는 흔한 구성이므로 오탐 빈도도 높다.

404 를 2점이 아니라 1점으로 두는 이유: 접근은 허용되지만 **AI 봇에 대한 의도적 정책이 없다.**
경쟁사가 검색봇을 명시 허용하고 학습봇을 분리 차단해 두면 그쪽이 우위다. 그 차이가 1점과 2점이다.

5xx 는 일시적 장애일 수 있으므로 **재시도 후에도 5xx** 일 때만 0점을 준다.

### 4.5 blocking 항목의 미판정 금지 (rubric v1.1.0~)

**`blocking: true` 항목은 미판정을 허용하지 않는다.**

게이팅은 0점에서만 발동한다. 그러면 항목을 아예 재지 않는 것으로 게이팅을 피할 수 있다.
실측 결과가 이렇다.

| `P1-01` 처리 | ARS |
|---|---|
| 0점으로 **채점** | **40.0** (원점수 97.5) |
| 사유 없이 **누락** | **100.0** |

감사를 안 하기로 선택하는 것만으로 60점이 생긴다. 대행사가 자기 고객 리포트를 뽑을 때
이 경로를 안 쓸 이유가 없으므로, 규칙으로 막는다.

blocking 2개(`P1-01`, `P1-03`)는 모두 `check: auto`라 기계 판정이 가능하다. 따라서
미판정에 정당한 사유가 거의 없다. 다만 사이트 다운·타임아웃처럼 **진짜로 못 재는** 경우는
존재하므로, 사유를 명시한 `unavailable` 상태를 둔다.

```yaml
gating:
  require_blocking_scored: true
```

```json
{
  "item_scores": { "P1-03": 2, "...": 2 },
  "unavailable": { "P1-01": "robots.txt 요청 타임아웃 (3회 재시도 실패)" }
}
```

**판정 규칙**

| 입력 | 결과 |
|---|---|
| blocking 항목이 0/1/2 로 채점됨 | 정상. 0점이면 게이팅 발동 |
| blocking 항목이 사유와 함께 `unavailable` | 통과. `gating_undetermined = true`, 사유를 리포트에 노출 |
| blocking 항목이 사유 없이 누락 또는 `null` | **거부 (422)** |
| `unavailable` 의 사유가 빈 문자열·공백 | **거부 (422)** — "안 쟀다"를 "못 쟀다"로 위장하는 통로 |
| 같은 항목이 채점과 `unavailable` 에 동시 존재 | **거부 (422)** |
| blocking 항목의 `unavailable_kind` 가 `not_applicable`·`design_limit` | **거부 (422)** (rubric v1.4.0~, §8.5) |

`gating_undetermined = true` 인 리포트는 **게이팅 여부를 판정하지 못한 리포트**다.
총점을 그대로 신뢰해서는 안 되며, 리포트 최상단에 그 사실과 사유를 표기한다.

> ⚠️ **게이팅 판정 불능 — 총점을 신뢰할 수 없습니다.**
> `P1-01` AI 크롤러 접근 허용 = 측정 실패 (robots.txt 요청 타임아웃, 3회 재시도 실패)
> 이 항목이 0점이면 총점은 40점으로 제한됩니다. 재측정을 권장합니다.

### 4.4 리포트 표기 (강제)

게이팅 발동 시 리포트 최상단에 원인 항목과 해제 조건을 명시한다.

> ⛔ **게이팅 발동 — 총점이 40점으로 제한되었습니다.**
> 원인: `P1-03` JavaScript 없이 본문 렌더링 = 0점
> 게이팅 미적용 시 점수: 64.6점
> 해제 조건: 주요 랜딩의 H1과 첫 문단이 원본 HTML에 포함되도록 SSR/SSG 적용
> **이 항목을 해제하기 전의 다른 개선은 AI 노출에 반영되지 않습니다.**

## 5. auto / manual 판정 항목 구분표

`check: auto`는 크롤러·파서·HTTP 클라이언트만으로 판정 가능한 항목,
`check: manual`은 외부 도구·계정 접근·사람 판단이 필요한 항목이다.

| Pillar | 총 항목 | auto | manual | manual 항목 |
|---|---|---|---|---|
| P1 | 10 | 9 | 1 | P1-10 |
| P2 | 10 | 10 | 0 | — |
| P3 | 9 | 8 | 1 | P3-08 |
| P4 | 9 | 2 | 7 | P4-02, P4-03, P4-04, P4-05, P4-06, P4-07, P4-09 |
| P5 | 7 | 5 | 2 | P5-05, P5-06 |
| **합계** | **45** | **34 (75.6%)** | **11 (24.4%)** | |

### 5.1 manual 항목 상세와 필요 입력

| id | 제목 | 판정에 필요한 것 |
|---|---|---|
| `P1-10` | 네이버 서치어드바이저 등록 및 Yeti 허용 | 네이버 웹마스터도구 계정 접근 (소유 확인·수집 진단 화면) |
| `P3-08` | NAP 일관성 | 네이버 플레이스·구글 비즈니스 프로필 리스팅 대조 |
| `P4-02` | 저자 자격 검증 가능성 | 외부 링크 실제 방문·동일 인물 확인 |
| `P4-03` | 권위 백링크 | 백링크 데이터 제공자 (Ahrefs/Semrush 등) |
| `P4-04` | 무링크 브랜드 언급 | 웹·커뮤니티 언급 모니터링, 자사 채널 제외 판단 |
| `P4-05` | 제3자 카테고리 정의 일치도 | 출처별 서술 수집 후 의미 일치 판단 |
| `P4-06` | 언론 커버리지 | 보도자료 전재 vs 원 기사 구분 (사람 판단) |
| `P4-07` | 원본 데이터·1차 관점 | 방법론 기재 여부의 질적 판단 |
| `P4-09` | 네이버 생태계 신뢰 신호 | 네이버 채널별 수동 조회, 자사/제3자 구분 |
| `P5-05` | 변경 이력 기록 | 이력 블록의 실질성 판단 (날짜만 vs 내용 요약) |
| `P5-06` | 콘텐츠 리뷰 운영 체계 | 고객 인터뷰 또는 내부 문서 제출 |

### 5.2 운영 함의

- **P4는 9항목 중 7개가 manual이다.** 이는 결함이 아니라 P4의 성질이다.
  권위는 사이트 밖에서 만들어지므로 사이트를 긁어서 알 수 없다.
- 따라서 **무료 셀프서브 진단은 P4를 채점할 수 없다.**
  무료 티어는 P1·P2·P3·P5의 auto 항목 30개만으로 부분 ARS를 산출하고,
  §3.1의 커버리지 규칙에 따라 P4 weight(20)를 제외한 뒤 재정규화한다.
  리포트에는 "P4 미채점 — 권위 진단은 유료 진단에서 제공"을 명시한다.
- 이 구조가 그대로 **무료 → 유료 전환 지점**이 된다. P4를 못 보면 Q2(준비만 된 상태)와
  Q4(미개척)를 구분할 수 없고, 그 구분이 처방을 완전히 갈라놓기 때문이다.

## 7. 링크 건전성 판정 — `unchecked` 와 `broken` 은 다르다 (rubric v1.3.0~)

`P5-04`(깨진 외부 링크)와 `P5-07`(내부 링크 건전성)은 같은 판정 규칙을 공유한다.
이 절이 그 규칙의 정본 근거다.

### 7.1 왜 분리했는가 — 파일럿 1회차(2026-09-05)가 드러낸 두 결함

v1.2.0 까지의 `P5-04`는 **"non-200 비율"** 하나로만 판정했다. 실측에서 두 결함이 나왔다.

**① 403·429 를 404 와 같이 셌다.** 대형 사이트가 진단용 User-Agent 를 봇으로 인식해
403(차단) 또는 429(레이트리밋)를 반환하면, 그 링크가 그대로 "깨진 링크"로 집계됐다.
**소셜·뉴스 링크를 정상적으로 많이 단 사이트가 그 이유만으로 감점됐다.** 파일럿 실행
로그에서 twitter·facebook·instagram·linkedin·kakao·네이버쇼핑라이브가 전부 진단용
UA 를 robots.txt 로 차단했다. robots 차단은 `status=None, failed=True` 로 떨어져
우연히 분모에서 빠졌지만, **403·429 는 `status` 값이 존재해 그대로 non-200 으로 셈됐다.**
의도한 동작이 아니라 우연히 맞게 돈 상태였다.

**② 내부 링크를 아예 재지 않았다.** `parsed.netloc == host` 인 링크는 판정 대상에서
제외됐다. 그런데 내부 404 는 **전적으로 자기 책임**이고 크롤러 도달성에 외부 링크보다
직접적으로 타격을 준다. 더 중요한데 측정되지 않고 있었다.

### 7.2 분모·분자 정의

| 분류 | 상태 | 분모(`checked`)에 포함 | 분자(`broken`)에 포함 |
|---|---|---|---|
| 정상 | 2xx, 3xx(체인 종료 후) | ✅ | — |
| **broken** | 404, 410, 5xx(재시도 후에도) | ✅ | ✅ |
| **unchecked** | robots.txt 차단, 401, 403, 429, 타임아웃, DNS 실패, 연결 실패 | ❌ | ❌ |

- **`unchecked` 는 "깨졌다"가 아니라 "확인하지 못했다"다.** 봇 차단(403)과 링크 소멸(404)은
  원인이 다르고, 전자에 페널티를 주면 정상적으로 신뢰도 높은 외부 사이트(소셜·뉴스·대형
  플랫폼)를 인용할수록 점수가 낮아지는 역유인이 생긴다.
- **분모는 "확인에 성공한 링크 수"다.** `unchecked` 는 분모·분자 어디에도 넣지 않는다.
  전체 링크 수를 분모로 쓰면 `unchecked` 가 많을수록 `broken` 비율이 인위적으로 낮아 보이는
  반대 방향의 왜곡이 생기므로, 그 왜곡은 §7.3 의 커버리지 규칙으로 별도 처리한다.
- **리다이렉트 체인이 3홉을 초과**하면 `broken` 은 아니지만 level 2(만점)를 막는다.
  체인이 길다는 것은 링크가 살아 있어도 유지보수가 안 되고 있다는 신호이기 때문이다.
  `broken` 비율이 이미 level 2 기준(외부 3% 미만·내부 1% 미만)을 만족하더라도 3홉 초과
  체인이 1건이라도 있으면 level 2 를 받지 못하고 **level 1 로 처리한다** — level 0(비율
  자체가 나쁨)과는 별개의 사유이므로 등급을 두 단계 낮추지 않는다. `broken` 비율이 이미
  level 1 구간(3~10%, 내부 1~5%)이거나 그 이상이면 체인 위반 여부와 무관하게 비율이
  정하는 등급을 그대로 적용한다.

### 7.3 `unchecked` 50% 초과 — 판정 자체를 하지 않는다

`unchecked` 비율(= `unchecked / (checked + unchecked)`)이 **50% 초과**면 이 항목은
`0/1/2` 로 판정하지 않고 `unavailable`(사유: unchecked 비율)로 처리한다.

**절반도 확인하지 못한 표본으로 낸 비율은 비율이 아니다.** 예를 들어 대상 링크 20개 중
18개가 타임아웃으로 `unchecked` 이고 남은 2개가 우연히 둘 다 살아 있으면 `broken` 비율은
0%(만점)가 되는데, 이는 "링크가 건전하다"가 아니라 "거의 아무것도 확인하지 못했다"는
뜻이다. 이 경우를 만점으로 두면 규칙 5(§5, `check: auto` 의 임의 대리 지표 금지)를 어기는
것과 같은 결과를 낳는다 — 측정 실패가 좋은 점수로 둔갑한다.

### 7.4 내부(`P5-07`)가 외부(`P5-04`)보다 엄격한 이유

| | 외부 (`P5-04`) | 내부 (`P5-07`) |
|---|---|---|
| level 0 | broken > 10% | broken > 5% |
| level 1 | broken 3~10% | broken 1~5% |
| level 2 | broken < 3% (+ 체인 3홉 이하) | broken < 1% (+ 체인 3홉 이하) |

외부 링크의 생사는 **제3자 사이트의 운영 상태**에 달려 있어 자사가 통제할 수 없는 변수가
섞인다. 반면 내부 링크는 **자사 콘텐츠 관리의 결과물 그 자체**다 — 페이지를 옮기거나
지우면서 리다이렉트를 걸지 않은 것은 변명의 여지가 없는 저작 실수다. 통제 가능성이 높을수록
기준을 엄격히 하는 것은 이 rubric 전체의 배점 원칙(§1의 "자사 통제 가능성"에 따른 P1·P2
우대)과 같은 논리다.

`P5-07`은 `P1-07`(상태코드 건전성)과 대상이 겹쳐 보이지만 관측 시점과 목적이 다르다.
`P1-07`은 **크롤러가 사이트 구조를 통해 도달한 URL 자체**의 상태를 재는 접근성(P1) 지표이고,
`P5-07`은 **본문 콘텐츠가 링크로 인용·참조하는 대상**이 계속 유효한지를 재는 신선도·운영(P5)
지표다. 같은 URL 이 두 항목 모두에서 관측될 수 있으나, 재는 것은 "크롤러가 사이트에
들어올 수 있는가"(P1)와 "콘텐츠가 계속 유지보수되고 있는가"(P5)로 서로 다르다.

### 7.4-1 일시 오류와 영구 오류를 같이 세지 않는다 (v1.9.0)

`P1-05`·`P1-07`·`P5-04`·`P5-07` 은 전부 "오류가 몇 건인가" 를 묻는다. 그 물음에는
**두 종류의 '오류'** 가 섞인다.

| 종류 | 상태코드 | 뜻 | 채점 |
|---|---|---|---|
| **영구 오류** | 400·403·404·410 등 4xx (429 제외) · 500 · 501 | 그 URL 은 실제로 없거나 서버가 그 요청을 처리하지 못한다 | **결함으로 센다** |
| **일시 오류** | 408 · 429 · 502 · 503 · 504 | 지금 확인하지 못했다. 다시 물으면 달라질 수 있다 | **분모에서 뺀다** |
| **확인 실패** | 상태코드 없음 (타임아웃·DNS·연결 거부) | 응답 자체를 못 받았다 | **분모에서 뺀다** |

일시 오류를 영구 오류와 함께 세는 것은 §4 가 금지하는 **"미측정을 0점으로"** 를
상태코드에서 되풀이하는 것이다. 특히 429(Too Many Requests)는 **우리가 만든 부하의
결과**일 수 있어, 그것을 사이트의 결함으로 채점하면 측정이 대상을 바꾼 뒤 그 변화를
대상의 성질로 보고하는 셈이 된다.

일시 오류로 분모에서 빠진 URL 은 **건수를 근거에 남긴다.** 빠진 사실을 적지 않으면
"확인한 URL 10개 중 오류 0건" 과 "3개가 429 라 7개만 확인했고 오류 0건" 이 같은 문장이
된다.

### 7.4-2 왜 비율이 아니라 건수인가 (v1.9.0)

v1.8.0 까지 이 두 항목은 백분율 밴드였다 — `P1-07` 은 "4xx/5xx 비율 10% 초과",
`P1-05` 는 "non-200 1% 이하". **참조 구현의 표본은 사이트당 9~20개 URL 이다.**

n=9 에서 오류 1건은 11.1% 다. 그래서 `level 1` 구간(2~10%)에는 **어떤 관측값도 들어갈
수 없었고**, 첫 오류가 곧장 최하 등급이 됐다. `P1-05` 의 1% 도 n=18 에서는 "0건" 을
뜻했다. **밴드가 표본이 표현할 수 있는 해상도보다 촘촘했다.**

실측(2026-09-17, mkiicorp.com): 5분 간격 두 측정이 ARS **46.4 / 56.7** 로 갈렸고 그
차이 전부가 이 두 항목이었다. 그 시각 사이트의 18개 URL 은 전부 200 이었다.

비율 자체가 틀린 것이 아니라, **비율을 쓰려면 그 비율의 불확실성을 같이 내야 한다**
(§2 의 규칙이 Plane A 에만 적용되는 것이 아니다). n=9 에서 오류 0건의 95% 구간은
[0%, 29.9%] 이고, 그 구간으로는 "2% 미만" 을 주장할 수 없다. 그래서 이 rubric 은 작은
표본에서 **주장할 수 있는 것만 주장한다** — 건수다. 표본 크기 `n` 을 근거에 함께 싣는다.

### 7.5 내부(internal) vs 외부(external) 판정 — 호스트 기준

`P5-04`와 `P5-07`을 가르는 것은 링크의 호스트(host)다.

- **내부**: 링크의 호스트가 진단 대상 사이트의 호스트와 **정확히 일치**하거나,
  `www.` 접두사 유무 차이만 있는 경우(`example.com` ↔ `www.example.com`).
- **외부**: 그 외 전부. **서브도메인은 다른 호스트이므로 외부다**
  (`blog.example.com`, `shop.example.com` 은 대상이 `example.com` 이어도 외부 링크).

**등록 도메인(eTLD+1) 기준이 아니라 호스트 기준이다.** 등록 도메인 기준을 쓰면
`blog.example.com`처럼 실제로는 다른 팀·다른 CMS·다른 배포 주기로 운영되는 서브도메인의
링크 건전성까지 진단 대상 사이트의 "내부"로 묶이는데, 그 서브도메인의 링크 관리 책임은
진단 대상 사이트 운영자에게 없을 수 있다. `P5-07`이 외부(P5-04)보다 엄격한 임계를 쓰는
근거(§7.4)가 "자기 책임"이므로, 책임 소재가 불분명한 서브도메인까지 내부로 묶어 엄격한
기준을 적용하는 것은 그 근거와 모순된다. `www.` 만 예외로 두는 이유는 동일 콘텐츠의 단순
별칭으로 운영되는 것이 사실상 표준 관행이기 때문이다.

### 7.6 `P2-06` 단락 길이 — 조각은 단락이 아니다 (v1.10.0)

파일럿 27곳 중 판정된 26곳이 **전부 1점**이었다. 원인은 둘이었다.

| 관측 (v1.9.0 기준) | 값 |
|---|---|
| "6문장 초과" 단락 비율 | 26곳 전부 **0~4%** |
| "2~4문장" 단락 비율 (level 2 조건 ≥70%) | **최고 29%** |

1. **분모가 UI 조각으로 채워졌다.** `<div>` 텍스트를 문단으로 세면 메뉴·가격·카드
   제목·버튼 문구가 전부 한 문장짜리 "문단" 이 된다. 그러면 잘 쓴 본문이 있어도
   2~4문장 비율이 70% 에 닿을 수 없다.
2. **등급이 망라적이지 않았다.** "6문장 초과 <10% 이면서 2~4문장 <70%" 는 0/1/2
   어디에도 없었고, 구현이 그것을 1 로 떨어뜨렸다. **모든 사이트가 그 칸에 있었다.**

그래서 이 항목은 글의 질이 아니라 **UI 조각의 비율**을 재고 있었고, 사이트를 전혀
구별하지 못했다.

**운영 정의 (v1.10.0)**

```
산문 단락 = 문장 수 ≥ 2 인 문단           (한 문장짜리 조각은 분모에서 뺀다)
표본      = 홈 + 표본 페이지 전체           (홈의 산문 단락은 중앙값 4개뿐이다)
long      = 산문 단락 중 6문장 초과 비율
good      = 산문 단락 중 2~4문장 비율

산문 단락 < 5        → 판정하지 않는다 (inconclusive)
long > 0.30          → 0
long < 0.10 ∧ good ≥ 0.70 → 2
그 밖               → 1        ← 망라적이다. 빈칸이 없다
```

**하한 5 의 근거.** 산문 단락이 3개면 긴 단락 1개가 33% 라 level 1 구간(10~30%)에
아무 값도 들어갈 수 없다 — 첫 긴 단락이 곧장 0점이 된다. §7.4-2 가 P1-05·P1-07 에서
고친 것과 같은 결함이다. 4개부터 1개 = 25% 가 구간 안에 들고, 5 는 level 2 의
"70% 이상" 이 4/5 = 80% 로 표현되는 최소다.

**결과 (저장 원문 재생, 27곳).** level 2 **23** · level 1 **2** · 미판정 **2**.
대부분이 통과한다. 이것은 결함이 아니다 — 이 항목이 잡으려는 "벽 같은 단락" 이
요즘 사이트에 실제로 드물기 때문이다. 옛 상수 1 은 **측정이 막혀서**, 새 다수 2 는
**관찰이 그래서** 나온 것이고, 둘은 다른 종류의 치우침이다. 떨어지는 사이트가 나올
때 이 항목이 정보를 준다.

## 8. 미판정 사유 분류와 커버리지 분모 (`unavailable_kind`) — rubric v1.4.0~

### 8.1 왜 필요한가 — 파일럿 2회차(2026-09-05)가 드러낸 결함

`unavailable`은 지금까지 "사유가 있는 미판정"이라는 단일 상태였다. 그런데 사유의 **성격**이
전혀 다른 다섯 가지가 그 안에 뭉쳐 있었고, 전부 같은 무게로 커버리지를 깎았다.

v1.3.0에서 P5 항목을 6→7개로 늘렸을 때, "항목을 추가하면 커버리지가 오른다"는 가정과
반대로 **P5 제외 대상이 파일럿 2·3곳(2회차 표본)에서 오히려 늘었다.** 새 항목(`P5-07`)이
채점되어도, 기존 항목(`P5-04`)이 더 엄격해진 판정 규칙(§7.3의 unchecked 50% 규칙)에 걸려
미판정으로 돌아서면 순증분이 상쇄되기 때문이다.

세 대상의 P5 커버리지가 전부 0.43(=3/7)으로 동일했지만 사유는 전부 달랐다.

> 아래 표는 2026-09-05 파일럿 2회차의 **실측**이다. 만들어낸 예시가 아니다.
> 대상은 사전 고지 없이 감사한 실제 사이트이므로 익명으로 적는다 — 이 절의 요점은
> 세 사유가 어떻게 다른가이지 누구인가가 아니다.

| 대상 | 미판정 항목 | 사유 | 실제 성격 |
|---|---|---|---|
| 사이트 A | `P5-04` | 본문에 외부 링크가 없어 broken 비율의 분모를 만들 수 없음 | 판정 대상이 존재하지 않음 |
| 사이트 B | `P5-04` | 외부 링크 확인 불가(unchecked) 비율이 67%로 과반 | 대상은 있으나 확인 실패 |
| 사이트 C | `P5-02` | 단일 크롤로는 "빌드마다 자동 갱신" 여부를 판정할 수 없음 | 관측 설계상 원리적 한계 |

외부 링크가 0건인 사이트에 "외부 링크 건전성"을 요구해 감점하는 것은 측정이 아니다.
반대로 67%가 차단돼 모르는 것을 안다고 치면, 그건 이 제품이 파는 정직성을 스스로 어기는
것이다. 이 셋을 같은 무게로 취급한 것이 v1.3.0까지의 설계 결함이다.

### 8.2 6분류 (rubric v1.5.0~ — `awaiting_manual` 추가)

| kind | 뜻 | judgeable 분모 |
|---|---|---|
| `not_applicable` | 판정 대상이 사이트에 존재하지 않는다 (외부 링크 0건, 블로그 없음 등) | **제외** |
| `design_limit` | 단일 관측으로는 원리상 판정 불가 (시계열 필요 등) | **제외** |
| `inconclusive` | 대상은 있으나 확인에 실패했다 (unchecked 과반, 파싱 실패 등) | 포함 |
| `no_collector` | 수집기가 없다 — 우리 로드맵 항목 (`ARCHITECTURE.md` §7-5 `UNCOVERED_AUTO_ITEM_IDS`) | 포함 |
| `input_missing` | 필요한 정식 입력이 없다 (`extra_urls`, 목표 질문 세트 등) | 포함 |
| `awaiting_manual` | `check: manual` 항목인데 사람 판정이 아직 없다 (§8.7) | 포함 |

### 8.3 분모에서 빼는 기준 — 한 줄

> **판정 대상이 사이트에 성립하지 않으면 뺀다. 우리가 모르면 남긴다.**

이 한 줄이 규칙의 전부다. `unavailable_kind`를 명시하지 않은 채 미판정으로만 남은 항목은
`inconclusive`와 동일하게 분모에 남는다 — **애매하면 남기는 쪽이 기본값**이다. 빼는 쪽으로
기울면 커버리지가 부풀려지고, 그것은 정확히 이 rubric이 하지 말아야 할 일이다(§7.3의
"측정 실패가 좋은 점수로 둔갑한다"와 같은 위반이다).

### 8.4 `judgeable` · `coverage` · `applicability`

```
judgeable      = 전체 항목 수 - (not_applicable 항목 수 + design_limit 항목 수)
coverage       = 채점된 항목 수 / judgeable          ← Pillar 제외 판정(§3.1)과
                                                        min_item_coverage 판정(scoring.md §4.1)에 쓴다
applicability  = judgeable / 전체 항목 수             ← 별도 공시. 낮다고 감점이 아니라 맥락이다
```

이 산식은 Pillar 단위(§3.1의 50% 기준)와 전체 45항목 단위(`plane_b.coverage`) 양쪽에
동일하게 적용한다. **두 숫자(`coverage`, `applicability`)를 항상 함께 낸다** — 하나로
"얼마나 쟀는가"와 "얼마나 잴 수 있었는가"를 동시에 답하게 만든 것이 이번 결함의 원인이었다.
`applicability`가 낮다는 것은 "이 사이트에는 이 rubric의 상당 부분이 애초에 해당되지
않는다"는 뜻이며 그 자체로는 감점 사유가 아니다.

**`judgeable == 0`인 Pillar** (그 Pillar의 모든 항목이 `not_applicable`/`design_limit`)는
`coverage`가 0/0으로 정의되지 않는다. 이 경우 §3.1과 동일하게 weight를 제외하고 나머지를
100으로 재정규화하되, 리포트에 노출하는 사유를 **"커버리지 부족"이 아니라 "이 Pillar는
이 사이트에 적용되지 않음"**으로 구분한다. 전자는 측정을 안 했다는 뜻이고 후자는 애초에
잴 것이 없었다는 뜻이라, 같은 문구로 뭉치면 운영자가 다음에 무엇을 해야 하는지를 오해한다.

### 8.5 blocking 항목은 `not_applicable`·`design_limit`을 쓸 수 없다

`P1-01`(AI 크롤러 접근 허용)과 `P1-03`(JS 없이 본문 렌더링)은 모든 사이트에 성립하는
조건이다 — "이 사이트에는 크롤러 접근이라는 개념 자체가 없다"는 상태는 존재하지 않고,
단일 관측으로 렌더링 여부를 못 재는 원리적 한계도 없다. 따라서 blocking 항목의
`unavailable_kind`는 `inconclusive`·`no_collector`·`input_missing`·`awaiting_manual` 중
하나여야 하며(다만 `awaiting_manual`은 §8.7이 설명하듯 `check: manual` 항목에만 의미가
있고 blocking 2개는 둘 다 `check: auto`이므로 실제로는 나타날 수 없다),
`not_applicable` 또는 `design_limit`이 지정된 blocking 항목은 §4.5의 "사유 없는 누락"과
동일하게 **거부(422)**한다. 이 제약은 `pillars.yaml`의
`gating.blocking_forbidden_unavailable_kinds`가 정본이다.

왜 필요한가: blocking은 §4.5의 규칙대로 "0/1/2로 채점" 또는 "사유를 명시한 unavailable"
중 하나여야만 게이팅 판정이 성립한다. 만약 blocking 항목에 `not_applicable`을 허용하면
그 항목이 judgeable 분모에서 통째로 빠지면서 **게이팅 자체가 성립하지 않는 상태**를
만들 수 있다 — 도달성 게이팅 항목을 "해당 없음"으로 처리해 게이팅을 우회하는 새로운
구멍이 생긴다. §4.5가 막으려던 것과 같은 종류의 우회이므로 같은 방식(거부)으로 막는다.

### 8.6 `check: auto`와의 관계

`no_collector`는 `check: auto`인데 참조 구현이 아직 담당하지 않는 항목(`ARCHITECTURE.md`
§7-5, 현재 11개)에 쓴다. **로드맵 결손이지 사이트의 문제가 아니므로** judgeable에는
남긴다 — 언젠가 구현되면 채점될 수 있는 항목이라는 뜻이고, 지금 빼면 "이 사이트에는 원래
그 항목이 없다"는 것과 구분되지 않는다.

### 8.7 `awaiting_manual` — `check: manual`의 미판정 (rubric v1.5.0~)

**왜 필요한가.** `check: manual` 항목 13개(`P1-09`·`P1-10`·`P2-01`·`P3-08`·
`P4-02`~`P4-07`·`P4-09`·`P5-05`·`P5-06` — `P1-09`·`P2-01` 은 rubric v1.8.0 에서 편입)가 아직 사람 판정을 받지 못했을 때 붙일 kind가 v1.4.0까지는 존재하지
않았다. 파일럿 3회차 dry-run 실측(대상 10개, 미판정 291건 중 kind 없는 것 220건 —
75.6%)이 이 공백을 드러냈다: 대상 1건 기준 미판정 28건 중 6건만 kind가 있었고 나머지
22건 중 11건이 `no_collector`(로드맵 미구현 `check: auto` 항목)와 11건이 `check: manual`
항목이었는데, 두 종류를 구분할 kind가 없어 전부 이름 없는 상태로 뭉쳐 있었다.

**왜 `no_collector`로 대신 쓰지 않는가.** `no_collector`는 "우리가 아직 구현 안 함 =
로드맵 우선순위 대상"이라는 뜻이다(§8.6). `manual`은 설계상 **영구히 사람 티어**이지
미구현이 아니다 — 언젠가 자동화될 예정이 아니므로 로드맵 결손 집계에 섞으면 "이번 스프린트
안에 없앨 수 있는 것"과 "구조적으로 계속 사람이 봐야 하는 것"을 구분할 수 없게 된다.

**왜 `input_missing`으로 대신 쓰지 않는가.** `input_missing`은 리포트에서 "고객이 값을
제공하면 즉시 측정된다"는 뜻으로 노출된다(예: `extra_urls`). 그런데 고객은 우리 수동
감사자의 판정을 대신 제공할 수 없다 — `input_missing`을 쓰면 고객에게 할 수 없는 행동을
하라고 지시하는 셈이 되어 §8.3의 "우리가 모르면 남긴다"는 원칙을 오도한다.

**분모 처리.** `awaiting_manual`은 `not_applicable`·`design_limit`과 달리 judgeable
분모에 **남는다**(§8.2). 규칙은 §8.3의 한 줄 그대로다 — "판정 대상이 사이트에 성립하지
않으면 뺀다. 우리가 모르면 남긴다." 사람이 아직 보지 않은 것은 우리가 모르는 것이지 이
사이트에 해당 항목이 없는 것이 아니다. 만약 분모에서 뺀다면 수동 감사를 건너뛸수록
커버리지가 좋아지는 우회로가 생기고, 그것은 §4.5(blocking 미판정 금지)가 막은 것과
정확히 같은 모양의 결함이 된다.

**`unavailable_kind`를 명시하지 않은 기존 리포트와의 관계.** §8.3에 따라 kind 미지정은
이미 `inconclusive`와 동일하게 분모에 남는 것으로 처리된다. `awaiting_manual`은 그 중
"사유가 `check: manual`이라서 못 쟀다"는 부분 집합에 **이름을 붙인 것**뿐이므로, 같은
입력에 kind를 미지정으로 둔 경우와 `awaiting_manual`로 명시한 경우의 ARS·coverage는
항상 동일하다 — 값 자체가 아니라 **왜 못 쟀는지의 가시성**만 달라진다.

**blocking과의 관계는 §8.5를 참조.** blocking 2개(`P1-01`·`P1-03`)는 둘 다
`check: auto`이므로 `awaiting_manual`이 나타날 수 없다 — 이는 별도 금지 목록이 필요
없는, 항목 정의 자체(`pillars.yaml`의 각 항목 `check` 필드)에서 나오는 결과다. 그래서
`gating.blocking_forbidden_unavailable_kinds`에는 `awaiting_manual`을 추가하지 않는다
— 그 목록은 "분모에서 빼는 kind만 금지한다"는 목적을 갖는데(§8.5), `awaiting_manual`은
분모에서 빠지지 않으므로 애초에 그 목적 밖이다.

## 9. 조치 분류 (`remediation`) — rubric v1.6.0~

### 9.1 왜 필요한가

채점(0/1/2)은 "무엇이 미달인가"를 말한다. 그런데 리포트를 받은 조직 내부에서
"이걸 누가 고치는가"는 여전히 불명확했다. 경쟁사(Rankrogic류) 진단은 항목을
"자동 적용 가능 / 매니지드 필요"로 나눠 이 문제를 처리하지만, 그 이분법은
**대행사가 직접 사이트를 고치는 모델**을 전제한다. 이 제품은 남의 사이트를
직접 고치지 않는다 — 중립적 측정 도구인 것이 이 모델의 전제다
(`ARCHITECTURE.md` §3: 대시보드·과금은 각자의 제품, 공유하는 것은 측정뿐). 그래서 "자동화 여부"가 아니라 **"어떤 종류의 일이고
조직 내 누가 그 일을 담당하는가"**로 분류한다.

`remediation`은 **채점에 관여하지 않는 순수 정보 필드**다. 같은 `item_id`는
rubric 버전이 같은 한 항상 같은 `remediation` 값을 갖는다 — 사이트마다,
진단마다 달라지지 않는다. ARS·raw_ars·pillar 점수·게이팅·커버리지 어느 산식도
이 필드를 입력으로 쓰지 않는다.

### 9.2 5분류

| 값 | 뜻 | 누구를 부르는가 |
|---|---|---|
| `config` | 사이트 설정·파일 하나를 바꾸면 끝난다. **오늘 끝난다** | 사이트 관리자 |
| `dev` | 템플릿·코드·인프라 수정이 필요하다 | 개발자 |
| `content` | 글·자료를 새로 쓰거나 고쳐야 한다 | 콘텐츠 담당 |
| `operations` | 사이트 밖 등록·프로세스·담당자 지정이 필요하다 | 운영·마케팅 |
| `earned` | **남이 해줘야 한다. 살 수 없고 벌어야 한다** | — |

정본 값·설명·호출 대상은 `pillars.yaml` 상단 `remediation_tiers` 블록이다.

### 9.3 왜 `earned`를 따로 두는가

백링크·언론 보도·제3자 언급(`P4-03`~`P4-06`)을 다른 조치 항목과 같은 "할 일
목록"에 넣으면, 그 리포트를 받은 조직은 **오늘 실행할 수 없는 일을 오늘
하라는 지시**로 읽는다. 자사 콘텐츠를 고치는 일과 제3자가 우리를 언급하게
만드는 일은 착수 가능 시점 자체가 다르다 — 전자는 담당자가 오늘 착수할 수
있고, 후자는 오늘 착수해도 결과가 언제 나올지 자사가 통제할 수 없다.

**"이건 못 하는 일이다"라고 명시적으로 말해주는 것 자체가 `earned` 티어의
값이다.** 다른 4개 티어와 섞어 "45개 중 이만큼 남았다"고만 세면, 조직은
통제 불가능한 항목까지 자기 역량 부족으로 오인하거나, 반대로 통제 가능한
항목을 "언젠가 저절로 될 일"로 미루는 두 방향의 오판이 모두 가능해진다.

### 9.4 배정 원칙과 집계

45항목 전부가 정확히 하나의 `remediation` 값을 갖는다. 합계는
`config 3 · dev 17 · content 17 · operations 4 · earned 4`다. 배정 기준은
"이 항목을 0→2로 올리려면 최종적으로 누구의 승인/실행이 필요한가"다 — 여러
직군이 함께 관여하더라도(예: 콘텐츠 작성 후 개발자가 배포) **실행 결정권이
있는 마지막 단계**를 기준으로 하나만 고른다. 항목이 추가될 때는 이 6개 값
(5분류 + 45라는 합계) 중 무엇이 바뀌는지 changelog의 `comparability`에 명시한다.

리포트의 `plane_b.remediation_counts`는 **채점된(score 0/1/2) 항목만** 티어별로
집계한다. 미판정 항목의 조치 티어를 세면 "안 잰 것"이 "할 일"로 둔갑해
커버리지가 낮은 진단일수록 "오늘 할 일이 적다"는 잘못된 인상을 준다.

## 10. 증거 등급 (`evidence_grade`) — rubric v1.7.0~

### 10.1 왜 신설했는가

AEO 표준 실태 조사(`STANDARDS.md`, 2026-09-10)가 확인한 것은 **AEO/GEO 표준이 존재하지
않는다**는 사실이다. 그렇다면 이 45항목은 무엇을 근거로 점수를 주는가? 항목마다 답이 다르다.

- `P1-01`(robots.txt)은 **IETF 표준이 메커니즘을 규정**한다. Disallow 면 크롤러가 오지 않는다.
- `P1-04`(llms.txt)는 **아무도 읽는다고 말한 적이 없다.** 표준도 없고 제공사 진술도 없으며,
  Google 공식 문서는 오히려 "새 AI 텍스트 파일이 필요 없다"고 반박한다.

v1.6.0 까지 rubric 은 이 둘을 구분할 어휘가 없었다. 같은 Pillar 안에서 같은 무게로 보였고,
**근거 없는 항목에 조용히 점수를 주는 상태**였다. 그것은 이 명세가 경쟁 도구에 대해
비판하는 바로 그 행동이다(`STANDARDS.md` §4).

### 10.2 무엇을 등급화하는가 — 인과가 아니다

> ⚠️ `evidence_grade` 는 **그 항목이 재는 메커니즘의 근거**를 등급화한다.
> **"이걸 고치면 AI 답변 노출이 오른다"는 인과를 주장하지 않는다.**
> `standard` 등급도 마찬가지다. 인과는 `avr-model.md` §6 의 회귀가 끝나기 전까지
> 어떤 등급으로도 주장하지 않는다.

이 구분을 놓치면 등급이 성능 보증으로 읽히고, 그 순간 이 필드는 정직성 장치가 아니라
마케팅 문구가 된다.

> ⚠️ 리포트의 `item_result.evidence`(배열)와 **다른 것이다.** 그쪽은 이 사이트에서
> 관측한 근거(URL·스니펫)이고, 여기는 항목 자체의 근거 강도로 사이트와 무관하게 고정이다.

### 10.3 값

정본 어휘는 `pillars.yaml` 상단 `evidence_grades` 블록이다.

| 값 | 뜻 | 현재 분포 |
|---|---|---|
| `standard` | 거버넌스가 있는 표준이 메커니즘을 규정한다 (RFC 9309, RFC 9110 등) | 6개 — P1-01, P1-02, P1-06, P1-07, P5-04, P5-07 |
| `provider_documented` | AI·검색 제공사의 공개 문서가 이 신호를 소비한다고 서술한다 | 14개 — P1-03, P1-05, P1-08, P1-09, P3-01, P3-02, P3-03, P3-04, P3-05, P3-06, P3-07, P3-09, P5-01, P5-02 |
| `observed` | 우리 측정으로 관계를 관측했고 표본 수를 공시할 수 있다 | 0개 (현재 없음) |
| `unverified` | 표준도 제공사 문서도 우리 관측도 없다. 업계 관행 | 25개 — P1-04, P1-10, P2-01, P2-02, P2-03, P2-04, P2-05, P2-06, P2-07, P2-08, P2-09, P2-10, P3-08, P4-01, P4-02, P4-03, P4-04, P4-05, P4-06, P4-07, P4-08, P4-09, P5-03, P5-05, P5-06 |

45항목 전부가 정확히 하나의 값을 갖는다.

### 10.4 `observed` 가 비어 있는 이유

우리에게 관측이 없어서가 아니다. **유의한 관측이 없어서**다. `avr-model.md` §5.2 의
실측은 n=3, p=0.083 으로 유의하지 않다. 유의하지 않은 관측을 근거 등급으로 승격시키면
이 필드 전체가 무의미해진다. **비워 두는 것이 이 등급의 정직한 상태다.**

### 10.5 `unverified` 가 25개인 이유

`P2`(추출성) 10개와 `P4`(권위) 9개가 통째로 여기 속한다. **개별 항목의 결함이 아니라
이 분야의 상태다.** 어떤 AI 제공사도 "답변 우선 구조로 쓰면 인용한다"거나 "백링크가
있으면 답변에 넣는다"를 문서화한 적이 없다.

그럼에도 이 항목들을 rubric 에 남기는 이유는 셋이다.

1. 우리 관측(§5.2)에서 실제로 인용된 URL 은 메타태그가 아니라 **질문에 답하는 콘텐츠
   페이지**였다. 방향이 시사된다 — 입증은 아니다.
2. 이 항목들은 검색 노출·사용자 경험 측면에서 독립적인 값을 갖는다.
3. **빼면 재지 못하고, 재지 못하면 §6 의 회귀를 영원히 못 돌린다.** 인과를 밝히려면
   먼저 데이터를 모아야 한다.

**단, 리포트는 이 상태를 공시한다.** `unverified` 항목의 미달을 "반드시 고쳐야 할 결함"
으로 제시하지 않는다. 고객이 예산을 어디에 쓸지 정할 때 이 등급이 필요한 정보다.

### 10.6 채점에 관여하지 않는다

`remediation`(§9)과 같은 순수 정보 필드다. ARS·raw_ars·Pillar 점수·게이팅·커버리지
산식 어디에도 `evidence_grade` 를 입력으로 쓰지 않는다. 같은 `item_id` 는 rubric 버전이 같은 한
사이트와 무관하게 항상 같은 `evidence_grade` 값을 갖는다.

### 10.6-1 순서에도 관여한다 — 점수가 아니라 **제시 순서**다

§10.5 는 "`unverified` 항목의 미달을 반드시 고쳐야 할 결함으로 제시하지 않는다" 까지만
말했다. 그 요구를 칩과 주석으로 지키고도 **순서로 어길 수 있다.**

`unverified` 는 25항목 · **57%** 의 배점을 차지한다(P2 10개와 P4 9개가 통째로 속한다,
§10.5). 조치 목록이 배점만 보고 정렬하면 그 57% 가 목록 위쪽을 차지한다. 화면이 옆에
"근거 없음" 을 적어 두어도 소용이 없다 — **고객은 문구가 아니라 순서를 따라간다.**

2026-09-16 실측: 어느 사이트에서 `P1-04`(llms.txt, `unverified`, Google 공식 문서가
"새 AI 텍스트 파일이 필요 없다"고 반박)가 점수 기여 **공동 1위**로 나왔다.

**규칙.** 같은 조치 분류 안에서 다음 순서로 제시한다.

    ① blocking      rubric 이 정한 게이팅 판정. 근거 등급이 이기지 못한다.
    ② 낮은 수준      0점이 1점보다 먼저. 판정이지 비교가 아니다.
    ③ 강한 근거      standard > provider_documented > observed > (등급 미부여) > unverified
    ④ 큰 배점        같은 근거끼리를 가른다.
    ⑤ 항목 id

**③이 ④보다 앞인 것이 이 규칙의 전부다.** 같은 수준이라면, 근거가 약한 항목에 더 큰
배점이 걸려 있다는 이유로 그것을 먼저 하라고 말하지 않는다. 반대로 ①·②는 근거를
이긴다 — 그 둘은 비교가 아니라 rubric 이 정한 판정이기 때문이다.

**등급 미부여(`evidence_grade` 없음)를 맨 뒤에 두지 않는다.** 그건 "근거 없음" 이라고
단정한 셈이다. 모르는 것과 없는 것을 구별하는 것은 이 명세 전체의 규칙이다(§8.3).

> ⚠️ 이것은 **§10.6 의 예외가 아니다.** ARS·pillar 점수·게이팅·커버리지 산식은 그대로
> `evidence_grade` 를 입력으로 쓰지 않는다. 바뀌는 것은 같은 점수를 **어떤 차례로
> 보여 주는가** 뿐이고, 항목을 지우거나 배점을 깎지도 않는다 -- §10.5 의 세 번째 이유
> ("빼면 재지 못하고, 재지 못하면 §6 의 회귀를 영원히 못 돌린다")가 그대로 유효하다.

### 10.7 갱신 의무

**등급을 올리는 것도 내리는 것도 우리 책임이다.** 어떤 제공사가 `llms.txt` 를 읽는다고
공개 진술하면 `P1-04` 는 즉시 `provider_documented` 가 되어야 하고, 그 진술을 찾는 일은
우리 몫이다. 근거가 생겼는데 `unverified` 로 방치하면 그것도 거짓 보고다
(`STANDARDS.md` §6).

## 11. 자동 진단의 도달 범위 — `check: manual` 이 만드는 천장

### 11.1 두 규칙을 합치면 나오는 결론

이 명세는 이미 두 규칙을 정했다.

- **§3.1** — pillar 커버리지가 하한(`min_pillar_coverage` = 0.5) 미만이면 그 pillar 를
  빼고 남은 배점을 100 으로 **재정규화**한다.
- **§8.7** — `check: manual` 은 설계상 **영구히 사람 티어**이며 judgeable 분모에 남는다.
  사람이 아직 안 본 것은 우리가 모르는 것이지 사이트에 해당 항목이 없는 것이 아니다.

둘을 합치면 결론이 나온다. **자동 판정만으로는 도달할 수 없는 pillar 가 존재한다.**

    자동 커버리지 상한 = (그 pillar 의 check:auto 항목 수) / (전체 항목 수)

이 값이 0.5 미만이면, 자동 항목을 **전부** 판정해도 §3.1 의 하한을 못 넘는다. 즉 그
pillar 는 자동 진단에서 **언제나** 제외된다. 회차의 사정이 아니라 rubric 의 성질이다.

### 11.2 현재 rubric(v1.7.0)에서 그런 pillar

**`P4`(권위, 배점 20) 하나다.** 9항목 중 7개가 `check: manual` 이라 자동 커버리지
상한이 `2/9` = `0.22` 이고, 하한 0.5 에 못 미친다.

2026-09-15 실측(국내 28곳, `docs/BASELINE_28.md`): **측정된 27곳 전부에서 P4 가
제외**됐다. 예외는 없었고, 위 유도에 따르면 앞으로도 없다.

> ⚠️ `check: manual` 이 **있다는 것만으로는** 여기 해당하지 않는다. `P5`(신선도·운영)도
> manual 이 2개 있지만 7항목 중 5개가 auto 라 0.71 로 하한을 넘는다.

### 11.3 그래서 자동 진단의 100 과 전체 진단의 100 은 다른 척도다

P4 가 빠지면 §3.1 에 따라 남은 80점이 **재정규화**되어 100 으로 보고된다. 그 결과 둘이
따라온다.

1. **자동 티어에서는 P4 를 잘하든 못하든 총점이 같다.** 권위 신호를 쌓은 브랜드와
   전혀 쌓지 않은 브랜드가 자동 진단에서 구별되지 않는다.
2. 자동 ARS 와 사람 판정을 포함한 ARS 를 **같은 임계값으로 비교하면 안 된다.**
   같은 이름을 쓰되 모수가 다르다.

### 11.4 리포트의 의무

리포트는 이 제외를 **커버리지 부족과 구별해서** 말해야 한다.

| | 뜻 | 고객이 할 수 있는 일 |
|---|---|---|
| 커버리지 부족 | 이번 회차에 덜 쟀다 | 입력을 더 주거나 다시 돌린다 |
| 자동 진단 범위 밖 | 설계상 자동으로는 판정하지 않는다 | **사람 판정(심화 진단)으로만 풀린다** |

둘을 한 문장으로 접으면 앞엣것으로 읽힌다. §8.7 이 `awaiting_manual` 을
`no_collector`·`input_missing` 과 구별한 것과 **정확히 같은 이유**다 — 고객에게 할 수
없는 행동을 하라고 지시하지 않는다.

그리고 층 게이지처럼 부분 점수를 그리는 화면은 **그 층에서 잰 배점과 전체 배점을 함께**
낸다(예: `인용 58.3/100 · 배점 20/40`). 각주로 내리면 읽히지 않고 숫자만 비교당한다.
